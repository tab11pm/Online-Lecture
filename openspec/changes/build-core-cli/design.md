# Design

## Context

Репозиторий содержит только `SPEC.md`. Согласованный change создаёт первый технический слой этапа A; мотивировка и границы перечислены в [proposal.md](proposal.md), а поведенческие контракты — в `specs/`.

## Goals / Non-Goals

**Goals:**

- Создать переносимое TypeScript-ядро, которое можно вызвать из CLI, а затем из Electron IPC.
- Обеспечить атомарное локальное хранение и детерминированную обработку времени.
- Сделать внешние интеграции заменяемыми портами, чтобы тестировать ядро без браузера и сети.

**Non-Goals:**

- Не запускать SDO MCP, Playwright или BigBlueButton и не проверять реальную авторизацию.
- Не создавать Electron UI, трей, Windows-автозапуск или установщик.
- Не выдавать технический YAML за пользовательский формат будущего приложения.

## Decisions

### Гексагональная граница ядра

`core` содержит доменные типы, автомат переходов, расчёт occurrence и порты `JobRepository`, `RunRepository`, `Clock` и `LectureRunner`. SQLite, YAML и процесс CLI находятся в адаптерах. Это выбранно вместо CLI-ориентированной структуры, чтобы Electron использовал те же правила без переноса логики; полноценный Electron shell сейчас добавил бы ненужную зависимость.

### SQLite как единственный источник состояния

Хранилище имеет версии миграций, таблицы заданий и запусков, и уникальный индекс `(job_id, occurrence_id)`. Операция получения или создания запуска выполняется транзакционно. Это надёжнее проверки в памяти и сохраняет защиту после рестарта. Резервная копия создаётся перед изменениями расписания; при ошибке открытия исходный файл переименовывается в диагностический, затем восстанавливается последняя валидная копия.

### Время и жизненный цикл

Все расчёты принимают IANA timezone задания и внедряемый `Clock`; время хранится с достаточной зоной/смещением, а не как локальная строка процесса. Автомат является таблицей разрешённых переходов. Планировщик создаёт `skipped` после дедлайна и инициирует выход по `leaveAt` из любого нетерминального состояния. Retry-политика — чистая функция, возвращающая `5s`, `15s`, `30s` или отсутствие следующей попытки.

### Тонкий CLI и безопасный конфиг

CLI преобразует аргументы и YAML в команды ядра, отображает пользовательские ошибки и не содержит правил планирования. Валидация требует ровно одну цель `search` или `url`; URL допускает только HTTPS и конкретную Moodle BBB-активность, а базовый BBB client URL отклоняется. Логи и ошибки проходят redaction cookies, query-параметров, join URL и `sessionToken`.

### Адаптер внешнего запуска как заглушка

Порт `LectureRunner` на этом change возвращает контролируемый результат без сети. `auth check` использует отдельный порт авторизации, который сообщает `not_configured`. В следующем change SDO MCP и BBB-адаптеры заменят эти реализации, не меняя контракты планировщика.

## Risks / Trade-offs

- [SQLite native dependency усложнит Windows packaging] → изолировать драйвер в persistence-адаптере и тестировать миграции в CI до Electron packaging.
- [DST и неявное локальное время дают неверный occurrence] → обязательный IANA timezone, внедряемые часы и тесты на границах дат.
- [Заглушка создаёт впечатление реального присутствия] → CLI явно помечает отсутствие SDO/BBB-адаптера и не переводит запуск в `connected`.
- [Повреждение базы может потерять последние изменения] → перед изменением расписания хранить ограниченную ротацию резервных копий и показывать результат восстановления.

## Migration Plan

1. Инициализировать workspace и создать миграцию начальной схемы.
2. Добавить ядро, адаптер SQLite и CLI за фиксированными портами.
3. Выполнить unit- и интеграционные тесты; CLI пока используется только разработчиками.
4. Для rollback удалить новый бинарный артефакт и базу, созданную в тестовой среде; пользовательских данных в текущем репозитории ещё нет.
