# Редактирование расписания в десктопе (slice 2b) — дизайн

**Дата:** 2026-10-18
**Статус:** на ревью
**OpenSpec:** `openspec/changes/desktop-schedule-editing`

## Цель и границы

Студент исправляет время отдельной импортированной пары, переносит её на другую дату и добавляет собственную разовую или еженедельную лекцию без командной строки. Обновление расписания ТУСУР сохраняет эти решения; планировщик входит в каждое фактическое вхождение не более одного раза.

Входит: правка времени конкретного импортированного вхождения, перенос, отмена переноса до запуска, ручная пара по ссылке на курс СДО или поисковому запросу, подтверждение BBB-активности, удаление пары, показ источника и действий в повестке. Уведомления, журнал и Windows-упаковка остаются в следующих этапах.

## Решение и альтернативы

Использовать существующие `Job`, `Schedule` и SQLite-таблицу `jobs`. Импортированные правки остаются в `ImportedOccurrence` с `edited`; скрытие исходной пары — с `suppressed`. Ручная пара — отдельный `Job` с `source: 'manual'`, типом `once` или `weekly` и подтверждённой целью. Связь переноса хранится в ручном задании как `rescheduledFrom: { jobId, date }`; `date` устойчив к смене `joinAt`.

Отдельная таблица переопределений сделала бы чтение исходного расписания проще, но потребовала бы миграции, синхронизации двух источников и изменений в планировщике. Только UI-поправка времени потерялась бы при следующем импорте. Текущая модель уже поддерживает `edited`, `suppressed`, `once` и `weekly`, поэтому первый вариант меньше меняет работающий поток.

## Данные и правила

- Добавить необязательные поля `Job.title?: string` для названия ручной пары и `Job.rescheduledFrom?: { jobId: string; date: string }` для связи переноса. Старые задания читаются без миграции содержимого; отсутствие `source` продолжает означать ручное задание. Повестка и дедупликация используют `title` ручной пары; отсутствие названия у старого задания сохраняет существующий fallback по `target.courseName`/`id`.
- Использовать часовой пояс `Asia/Krasnoyarsk`, показанный рядом со временем. Для всех новых и изменённых пар требовать корректные дату/время и `joinAt < leaveAt` в пределах одного дня. Вход должен быть в будущем; пустые дни недели и неподдерживаемые URL отклоняются до записи.
- Править или переносить можно только ещё не начавшееся вхождение: в нём нет записи `Run`, кроме безопасного статуса `scheduled`, и время входа ещё не наступило. Перед записью снова читать задание и запуск из БД. Уже идущие и завершённые вхождения нельзя менять задним числом.
- Изменение времени импортированной пары заменяет её `joinAt`/`leaveAt`, ставит `edited: true` и сохраняет прежние `room`/`suppressed`. Поскольку `occurrenceId` включает время входа, старый ID после правки больше не является текущим; разрешение правки до запуска не даёт создать второй запуск.
- Перенос в одной транзакции помечает исходную импортированную пару `suppressed: true` и создаёт ручную `once` с `rescheduledFrom`. Название и цель исходного задания переходят в новую пару; при запуске цель вновь разрешается через MCP. Уже подавленную пару перенести нельзя. Повторная команда с тем же источником не создаёт вторую замену.
- «Отменить перенос» до начала любого из двух запусков удаляет связанную ручную пару и снимает подавление исходной в одной транзакции. После начала запуска действие недоступно; пользователь видит причину.
- Удаление обычной ручной пары удаляет её задание; историю запусков не удаляет. Удаление импортированной пары помечает только выбранное вхождение `suppressed`. Для связанной пары используется действие «Отменить перенос», чтобы исходное вхождение не осталось скрытым неожиданно.
- При создании ручной пары совпадение по местной дате, времени входа и нормализованному имени дисциплины с импортированной парой немедленно подавляет импортированное вхождение. То же правило применяется при последующем импорте, включая дни еженедельной пары. Для сравнения использовать явное `title`, а не пустую дисциплину, которая в текущем merger означает совпадение с любой дисциплиной. Сохранение ручной пары и подавление уже известных дублей атомарно.
- Все изменения сериализуются с записью импорта в worker. Импорт повторно читает БД непосредственно перед merge, чтобы сохранить последние `edited`/`suppressed` и ручные задания.

## Подтверждение цели и безопасность

Мастер принимает ссылку на курс `sdo.tusur.ru/course/view.php?id=…` либо текст поиска. Worker вызывает существующий `resolve_online_lecture` через SDO MCP. Результат `resolved` показывает название курса и BBB-активности для подтверждения. При `ambiguous` пользователь выбирает одну из найденных активностей; `not_found` оставляет форму для исправления; `auth_required` направляет к повторному входу. Сохранение без подтверждённой активности запрещено.

Worker держит соответствие краткоживущих непрозрачных ID кандидатов и URL активности в памяти до сохранения/отмены формы. Renderer получает только имена, тип активности и ID; курсовые и BBB URL не попадают в снимок или сообщения об ошибках. Введённая пользователем ссылка передаётся только в команду поиска, не пишется в лог. После рестарта worker мастер начинает поиск заново.

## Компоненты и поток

- `src/core/schedule-editing.ts`: чистые правила валидации, правки импортированного вхождения, переноса и удаления; вход по `jobId` и устойчивому ключу даты (текущий импорт хранит не более одного вхождения данного задания на дату), без доверия к переданным renderer данным расписания.
- `src/persistence/job-repository.ts`: транзакционная запись нескольких заданий и проверка текущего состояния запуска; создание резервной копии перед изменением, как в существующих методах.
- `apps/desktop/src/worker/lecture-service.ts`: сериализует команды редактирования с импортом, обновляет повестку и инициирует внеочередной тик планировщика после успешной записи. Поиск BBB вынесен в отдельный адаптер worker; сетевой запрос выполняется вне транзакции.
- Типизированные команды `lectures.editImportedTime`, `lectures.reschedule`, `lectures.cancelReschedule`, `lectures.resolveManualTarget`, `lectures.saveManual`, `lectures.delete`; main и preload только пересылают и валидируют входы. В ответах и `LecturesView` нет URL.
- `AgendaItem` получает `source`, `editable`, `rescheduledFrom`/признак замены и `title`. Это позволяет показывать корректные действия без раскрытия хранимой цели.

## Интерфейс

Главный экран сохраняет текущую структуру. Над повесткой появляется «Добавить пару». В каждой строке будущей пары — контекстные действия «Изменить время», «Перенести» или «Удалить», а связанная разовая пара показывает «Отменить перенос». Недоступные действия имеют понятное объяснение; текущую лекцию по-прежнему можно остановить отдельно.

Мастер ручной пары идёт по четырём шагам: курс (ссылка или поиск) → разово/еженедельно → время входа/выхода → подтверждение BBB-активности и сохранение. Состояния поиска, неоднозначности и ошибки остаются в той же форме. Поля имеют видимые подписи, ошибки рядом с полями и клавиатурный фокус; дата и время показывают часовой пояс. Нельзя сохранить форму повторным нажатием во время записи. Вариант редактирования времени открывает короткую форму с текущими значениями, перенос — форму даты и времени с явным указанием исходной пары.

**Основание UI:** существующие `MainScreen`, `AgendaList` и `CredentialsForm` задают текущий визуальный и компонентный язык; локальный Refero `craft-details.md` — подписи полей, `aria-invalid`, сообщения об ошибках, состояние отправки, доступные кнопки и клавиатурный фокус. Живой поиск Refero недоступен (подписка неактивна), поэтому новая визуальная система не вводится. При реализации сохранить текущие компоненты и проверить интерфейс на реальном рендере.

## Проверка

Тесты ядра проверяют временные границы, недельные дни, `edited` после полного/частичного импорта, подавление дублей, отсутствие повторного переноса и неизменность истории запусков. Тесты SQLite проверяют атомарность переноса/отмены, резервную копию и гонку с импортом. Контрактные тесты MCP проверяют `resolved`, `ambiguous`, `not_found`, `auth_required` и отсутствие URL в IPC. Тесты worker и renderer проверяют полный мастер, ошибки, повторное нажатие, правку и перенос. E2E на фиктивной сессии проверяет создание разовой пары и перенос. Ручная Windows-проверка остаётся в `HANDOFF.md` без реального входа в чужую лекцию.
