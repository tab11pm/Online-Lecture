# Windows-упаковка Online Lecture — дизайн

**Дата:** 2026-10-19  
**Статус:** проект на согласование; реализация не начата  
**OpenSpec:** `openspec/changes/windows-packaging/`

## Цель и актуальные ограничения

Нетехнический пользователь устанавливает Online Lecture одним `.exe` и работает без системных Node.js, npm, MCP или SQLite. На Windows используется Edge по умолчанию; Chromium в установщик не входит и скачивается только кнопкой внутри приложения. Это уточнённое пользователем требование, отражённое в `SPEC.md` и `chromium-choice-install`.

Этап охватывает воспроизводимую упаковку существующего приложения и проверку упакованного runtime. Планировщик, правила посещения, интерфейс и реальный SSO не перепроектируются. Linux-проверки не выдаются за успешную установку на Windows.

## Выбранный вариант и альтернативы

Предлагается обычный NSIS-установщик для текущего пользователя, без повышения прав. Первая цель сборки — Windows x64. Это рабочее ограничение первого артефакта, а не заявление об отказе от других архитектур навсегда. Имя продукта — `Online Lecture`, стабильный `appId` — `ru.onlinelecture.desktop`, имя исполняемого файла — `OnlineLecture.exe`.

Альтернативы: portable проще для разовой проверки, но не закрывает установку/удаление и интеграцию с Windows; MSI/per-machine добавляет администраторский сценарий, который сейчас не требуется. В этом этапе они не создаются.

Первый артефакт предназначен для тестирования и может быть неподписанным: это явно указывается в инструкции вместе с возможным предупреждением Windows. Сертификат, покупка подписи, публичный релиз, автообновления и сетевые публикации не входят в задачу. Защиты Windows не отключаются. Сборка использует `--publish never`.

## Состав и расположение файлов

`electron-builder` остаётся в установленной major-версии 26. Код main, preload, worker, renderer и локальные шрифты упаковываются в `resources/app.asar`. Только production-граф зависимостей desktop-пакета распаковывается в `resources/app.asar.unpacked/node_modules/`: там доступны SDO MCP, Playwright CLI, `playwright-core` и их транзитивные зависимости. На первом этапе распаковывается весь production-граф, а не хрупкий список отдельных модулей; dev-зависимости туда не добавляются.

`better-sqlite3` становится явной production-зависимостью desktop; `jsdom` переносится из desktop devDependencies в dependencies. Используются уже зафиксированные lockfile версии. Не допускается сборка, работоспособная только благодаря родительскому `node_modules` исходного репозитория. Автоматический rebuild общих workspace-модулей при упаковке отключается; отдельная Electron-native сборка сохраняется.

Ресурс `resources/native/better_sqlite3.node` копируется из отдельной native-сборки. В packaged-режиме путь определяется через `process.resourcesPath`, в dev остаётся существующий `apps/desktop/native`. Node-native бинарник из общего `node_modules/better-sqlite3/build` в установщик не включается: runtime использует явный `nativeBinding`.

Ожидаемая структура:

```text
OnlineLecture.exe
resources/
  app.asar                         # out/main, out/preload, out/renderer, manifest
  app.asar.unpacked/node_modules/  # production runtime-граф
  native/better_sqlite3.node       # Windows x64, ABI текущего Electron
```

Не поставляются исходные тесты, preview-сценарии, `.env`/`.env.*`, auth storage state, пользовательские SQLite/backup-файлы, логи, browser profiles, диагностические архивы, Electron-native build workdir и скачанные браузеры. Проверка состава учитывает файлы и внутри ASAR, и рядом с ним. Собственные файлы приложения выбираются allowlist-правилами; сторонние LICENSE/NOTICE сохраняются. Проверка не запрещает служебные файлы SQLite внутри исходников сторонних библиотек по одному расширению без учёта их назначения.

## Нативная сборка и команды

Windows-артефакт собирается на Windows x64. На Linux разрешены unit-тесты и проверка конфигурации, но не копирование Linux `.node` в Windows-артефакт. До упаковки проверяются target platform/architecture, stamp с версиями Electron/better-sqlite3 и заголовок PE/архитектура native-бинарника; неверный или отсутствующий ресурс даёт ненулевой выход до создания артефакта.

Предлагаемые команды desktop workspace: `pack:win` создаёт распакованный тестовый пакет; `dist:win` — NSIS `.exe`. Обе выполняют проверку совпадения версий Playwright, desktop build/native build и проверку ресурсов. Артефакты размещаются в игнорируемом `apps/desktop/dist/`. Выпуск сопровождается SHA-256 готового `.exe`; это контроль целостности, не замена цифровой подписи.

Системные Node.js, Python и C++ Build Tools могут требоваться на машине разработчика для сборки. Они не требуются пользователю установленного приложения. Linux developer workflow и Node-native SQLite для core-тестов не повреждаются.

## Окружение и запрет `.env` в установленном приложении

`app.isPackaged` определяет packaged-политику; флаг нельзя подменить обычной переменной окружения. Main не вызывает `loadEnvFiles` в packaged-режиме. Worker получает эту политику внутренним типизированным контрактом, без нового публичного renderer API. В dev чтение `.env` и приоритет явно заданных SDO-настроек сохраняются.

Одного запрета в main недостаточно: текущий `sdo_mcp` импортирует `dotenv/config`. Для bundled MCP в packaged-режиме dotenv принудительно направляется на пустое системное устройство (`NUL` на Windows, `/dev/null` в Linux-проверке) через явную конфигурацию дочернего процесса. Путь и quiet-режим задаются после формирования окружения и не переопределяются настройками из `.env`/унаследованными dotenv-опциями. В subprocess не передаются произвольные дополнительные аргументы dotenv. `ELECTRON_RUN_AS_NODE=1` сохраняется; системный Node не ищется.

Проверка с подложным `.env` в cwd должна доказать, что sentinel-переменные не загружены, параметры запуска MCP не подменены, а stdout остаётся MCP-протоколом. Нужен отдельный тест с реальным установленным dotenv, а не только проверка объекта окружения. Файлы `node_modules` не патчатся.

SDO MCP и Playwright запускаются из распакованных путей без shell, с корректной передачей путей с пробелами и кириллицей. Пароли, cookies и адреса встречи не попадают в сообщения ошибок упаковки или smoke-отчёт.

## Пользовательские данные и интеграция Windows

Данные остаются в `%LOCALAPPDATA%/OnlineLecture`, отдельно от каталога программы. Обновление поверх установленной тестовой версии сохраняет базу, настройки и сессию. Удаление программы по умолчанию сохраняет эти данные; автоматическая очистка аккаунта не добавляется. Общий кэш браузеров Playwright не удаляется установщиком или uninstaller.

Автозапуск остаётся выключенным до явного выбора пользователя. Uninstaller удаляет только регистрацию автозапуска самого Online Lecture и собственные ярлыки. Установка/удаление требует завершения работающего приложения; нельзя молча заменять работающие ресурсы. Проверка завершения активной fake-лекции входит в Windows smoke.

Main устанавливает тот же `appId` для Windows-уведомлений до создания окна. Single-instance guard до запуска worker не позволяет второму экземпляру создать второй планировщик; повторный запуск открывает существующее окно. Закрытие окна по-прежнему скрывает его в трей, «Выход» завершает worker и браузеры по существующему протоколу.

DPAPI не заменяется fallback-механизмом: если шифрование на Windows недоступно, пароль не сохраняется. Схема хранения и существующие пути данных не меняются.

## Браузер после установки

Edge не скачивается инсталлятором. Если он недоступен, приложение не должно заявлять об успешной браузерной операции: пользователь может выбрать и установить Chromium существующим UI. Отдельное автоматическое скачивание Chromium, изменение браузера без согласия и новая система управления кэшем не добавляются.

Кнопка Chromium запускает распакованный CLI через Electron Node. Проверяются основной Chromium и headless shell нужной версии; ошибки/повтор и сохранение выбора остаются как в `chromium-choice-install`. Тесты проверяют одинаковые browser options для SDO MCP, импорта и BBB. Загрузка по сети на Windows выполняется только явно запущенным ручным smoke-сценарием.

## Приёмка и границы доказательств

1. Unit/integration: dev/packaged пути с пробелами и кириллицей; `.env` разрешён только в dev; защита MCP от dotenv; native stamp/PE/архитектура; appId/single-instance; отсутствие автозапуска по умолчанию.
2. Проверка содержимого реально собранного пакета: обязательные ресурсы и production-граф присутствуют, запрещённых данных нет; подложный отсутствующий/неверный native-модуль отклоняется проверкой. Чтения одного YAML-конфига недостаточно.
3. Windows packaged fake-session E2E запускает именно упакованный `OnlineLecture.exe`, с отдельными временными данными. Покрывает вход, fake импорт/лекцию/остановку/журнал и добавление/перенос/удаление. Изолированная проверка MCP-handshake и распакованного CLI не обращается к ТУСУР и не скачивает браузер без отдельного действия.
4. Чистая Windows без developer Node/npm/репозитория: установка, Edge, загрузка Chromium кнопкой и повтор после ошибки, DPAPI, трей, уведомление/переход в журнал, явный автозапуск, повторный запуск, завершение приложения, обновление и uninstall. Для CLI установки Chromium проверяется действительный запуск, а не только вычисление пути.
5. Реальный SSO/BBB остаётся ручной отдельной проверкой с разрешённой учётной записью и лекцией. Секреты не нужны ни для unit-тестов, ни для сборки, ни для fake-session E2E.

Windows-результаты фиксируются только при фактическом запуске на Windows. Если доступен лишь Linux, handoff содержит выполненные проверки и явно незакрытые Windows-пункты; установщик не объявляется готовым к публичному выпуску.
