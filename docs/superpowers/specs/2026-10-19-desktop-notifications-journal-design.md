# Уведомления и журнал десктопа (slice 3) — дизайн

**Дата:** 2026-10-19

**Статус:** утверждён, реализован; ручная проверка Windows ожидается

**OpenSpec:** `openspec/changes/desktop-notifications-journal`

## Цель и границы

Студент видит, что произошло с каждой лекцией, и узнаёт о событиях, требующих внимания, даже когда окно свёрнуто в трей. История запусков и ошибок остаётся доступной после перезапуска. Пользовательские тексты не раскрывают сессию, внутренние URL и токены.

Входит: системные уведомления по событиям из `SPEC.md` §10, раздел «Журнал» с историей запусков и ошибок, безопасные сообщения и проверка повторных событий. Существующий `core.log` остаётся техническим диагностическим файлом. Экспорт архива, Telegram, новые настройки уведомлений и Windows-упаковка находятся вне этого slice.

## Выбранный подход

Источником истории запусков служит существующая таблица `runs`; она уже переживает удаление задания. Отдельная таблица `desktop_events` хранит ошибки входа, импорта и ядра и события, которым нужен устойчивый ключ для подавления повторов. Записи содержат время, тип, безопасный код, необязательные `jobId`/`occurrenceId` и безопасное название на момент события. Произвольные тексты исключений, URL и данные авторизации в эту таблицу не пишутся. Новую таблицу создаёт идемпотентное обновление схемы SQLite; восстановление из резервной копии и CLI сохраняют работоспособность.

Worker формирует типизированное событие в точке перехода состояния. Для завершения лекции сначала сохраняется `Run`, затем создаётся событие с уникальным ключом `jobId + occurrenceId + terminal status`; повторная публикация снимка или рестарт не создают дубль. Для ошибок импорта, входа и ядра ключ относится к одной попытке операции. `connected`, промежуточные состояния и уже существующие строки при старте не вызывают уведомление. При обрыве между записью `Run` и созданием события история запуска всё равно берётся из `runs`; повторное чтение терминальных запусков при старте восстанавливает недостающее событие без показа старого уведомления. Класс «повторы исчерпаны» передаётся как отдельный код из контроллера лекции, а не выводится только из `failed/error`: такой статус возможен и при другой ошибке.

Альтернатива — выводить уведомления по сравнению соседних снимков `LecturesView`: это не хранит контекст ошибки и теряет события при перезапуске. Разбор строк `core.log` смешал бы диагностический текст с UI и усложнил бы защиту секретов. Поэтому используется типизированный журнал событий поверх существующего хранилища запусков.

## События и уведомления

| Причина | Запись в журнале | Системное уведомление |
| --- | --- | --- |
| Успешный интерактивный вход | Событие `login_succeeded` | Да; восстановленная сессия при старте не считается новым входом |
| Выход из лекции | Терминальный `Run` и событие `lecture_finished` | Да; название и итог без URL |
| Требуется повторный вход | Событие `auth_required` | Да, один раз на эпизод до следующего успешного входа |
| Неоднозначный поиск BBB | Событие `search_ambiguous` | Да, один раз на запрос поиска |
| Ошибка импорта или ядра | Событие `import_error` или `core_error` | Да, один раз на попытку; подробности остаются в `core.log` |
| Повторы входа в лекцию исчерпаны | Терминальный `Run` и событие с отдельным кодом `retries_exhausted` | Да; не дублировать общим уведомлением об ошибке |

`completed`, `blocked` и `failed` отображаются разными пользовательскими статусами. `skipped` остаётся в истории, но не даёт системного уведомления. Ошибки входа и импорта используют безопасные коды, по которым renderer показывает заранее определённые русские сообщения. Редакция текста применяется также на границе worker → main; main не доверяет произвольной строке от worker. При недоступности системных уведомлений история и работа ядра продолжаются.

Main получает только новое событие с ID и безопасным кодом, создаёт Electron `Notification`, а по нажатию показывает окно и открывает журнал. Main не воспроизводит события из прошлого при запуске. Повторный IPC с тем же ID не показывает уведомление второй раз в рамках процесса. События, возникшие при свёрнутом окне, доставляются так же, как при открытом.

## Журнал и границы данных

Кнопка «Журнал» на главном экране открывает раздел в текущем окне. По умолчанию показываются последние 50 строк в обратном порядке времени: дата и время, название лекции или подсистемы, статус и короткая причина. Переключатель «Все / Ошибки» фильтрует данные на стороне worker. Следующая страница запрашивается явным действием; запрос ограничен размером страницы и использует устойчивый курсор, чтобы новые записи не сдвигали уже показанные. Для пустой истории и ошибки загрузки предусмотрены разные состояния.

Запуск остаётся виден после удаления ручной пары: название, известное до удаления, сохраняется в событии; для старых запусков без такого события показывается безопасный fallback «Лекция» и ID не выводится как заголовок. Список запусков строится из `runs` и событий без копирования `Run` в отдельную таблицу. Действия по изменению истории в UI нет. Полный технический лог не показывается на экране; путь к нему остаётся доступен в существующих сообщениях диагностики.

Через IPC передаётся только типизированная модель строк журнала: непрозрачный ID, время, категория, безопасный заголовок, статус и код причины. Raw `Run`, `Job.target`, текст исключения и содержимое `core.log` в renderer не попадают. Main проверяет параметры запроса, worker ограничивает выборку. Все имена от внешних систем проходят `redactSensitiveText` перед записью события и передачей в UI.

## Компоненты и поток

- `src/persistence`: таблица и репозиторий событий, ограниченная постраничная выборка запусков и событий. Уникальный ключ события обеспечивает идемпотентность.
- `apps/desktop/src/worker`: преобразование переходов `Run`, онбординга и импорта в события; формирование безопасной модели журнала и отправка только новых событий в host.
- `apps/desktop/src/shared`: узкие типы события, страницы журнала и IPC-команд.
- `apps/desktop/src/main`: проверка IPC, Electron `Notification`, обработка клика и передача навигации в renderer. Ошибка ОС при показе уведомления не влияет на лекцию.
- `apps/desktop/src/renderer`: кнопка «Журнал», список, фильтр и состояния загрузки/пустого результата; возврат к главному экрану сохраняет текущий `LecturesView`.

## Основание интерфейса

Существующие `MainScreen`, `LectureStatus` и текстовые статусы задают визуальную основу: компактный список, ясные названия и прямые действия без новой дизайн-системы. Локальный Refero `craft-details.md` задаёт видимый клавиатурный фокус, подписи, состояния загрузки и `role="status"`/`role="alert"`; живой поиск Refero был недоступен из-за неактивной подписки. При реализации проверить фактический рендер и читаемость длинных названий и узкого окна.

## Проверка и ограничения

Тесты проверяют: одно событие и уведомление на терминальный переход; отсутствие повторов после повторной публикации, рестарта worker и восстановления истории; отдельные уведомления для нового входа и `auth_required`; неоднозначный поиск и исчерпание повторов; сохранение истории после удаления задания; порядок, фильтр и курсор; отсутствие URL, cookies, query-параметров и токенов в SQLite, IPC и тексте уведомления; работу при отказе ОС показывать уведомление. Renderer-тесты проверяют загрузку, пустое состояние, ошибку, фильтр и переход по нажатию уведомления. Electron E2E использует фиктивную сессию; системный toast проверяется вручную на Windows.

Живые BBB-состояния waiting-room, завершение организатором и удаление модератором пока не подтверждены фикстурами. Журнал показывает только реально достигнутые состояния ядра и не пытается распознать их по непроверенным селекторам.
