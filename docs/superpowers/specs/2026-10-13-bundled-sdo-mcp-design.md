# SDO MCP как зависимость приложения и диагностика запуска — дизайн

**Дата**: 2026-10-13
**Статус**: Draft — на ревью
**Проект**: Online Lecture для SDO ТУСУР
**Фаза**: 3 (Windows Electron приложение), доработка онбординга
**OpenSpec**: `openspec/changes/bundle-sdo-mcp`
**Связанные документы**: [2026-10-02-electron-onboarding-design.md](2026-10-02-electron-onboarding-design.md)

## 1. Проблема

Приложение не выполняет вход само, а запускает SDO MCP (`tab11pm/sdo-mcp`) и вызывает
`sdo_login`/`check_sdo_auth`. Сейчас путь к серверу берётся из `SDO_MCP_SERVER_PATH` или
`~/.local/bin/sdo-mcp`. На машине обычного пользователя Windows ни того, ни другого нет:
нужно склонировать sdo_mcp, поставить Node.js, выполнить `npm install`, `npm run build`,
`npx playwright install chromium` и прописать путь в `.env`. Тест на компьютере друга
показал, что без этого приложение молча падает на этапе проверки сессии, а пользователь
видит «Выполните вход» вместо настоящей причины.

## 2. Цель

- sdo_mcp приезжает вместе с приложением через `npm install` и запускается без установленного
  Node.js и без ручной настройки путей.
- Если sdo_mcp всё же не запускается, пользователь видит понятное сообщение с причиной, а
  подробности (команда, код выхода, хвост stderr) пишутся в локальный лог без секретов.

## 3. Что входит и что не входит

Входит:

- Изменения в репозитории `sdo_mcp`, чтобы его можно было ставить как git-зависимость, и
  новый тег `v1.2.0`.
- Зависимость `sdo_mcp` в `online-lecture` и поиск её точки входа.
- Запуск сервера через Node, встроенный в Electron (`ELECTRON_RUN_AS_NODE=1`), а в CLI —
  через текущий `node`.
- Классификация ошибок запуска, отдельное сообщение в онбординге и файловый лог ядра.

Не входит:

- Настройка `electron-builder` и сборка установщика (фаза 4). Дизайн фиксирует требования к
  ней (раздел 8), но конфигурацию не добавляет.
- Выбор папки sdo_mcp в интерфейсе. От него отказались в пользу зависимости; переопределение
  для разработчиков остаётся через `SDO_MCP_SERVER_PATH`.
- Автоматический повторный вход с сохранённым паролем, распознавание неверного пароля по
  ответу sdo_mcp и ручной вход при капче — отдельные задачи.

## 4. Изменения в `sdo_mcp` (tab11pm/sdo-mcp)

1. **Установка из git.** В `package.json`:
   - `"main": "dist/index.js"` (сейчас опечатка `srd/index.js`);
   - `"prepare": "tsc"` — npm выполняет его при установке git-зависимости, временно ставя
     devDependencies;
   - `"files": ["dist"]` — обязательно: без него npm использует `.gitignore` как
     `.npmignore`, а там есть `dist/`, и собранный код не попадёт в `node_modules`;
   - `"bin": { "sdo-mcp": "dist/index.js" }` и shebang `#!/usr/bin/env node` в `src/index.ts`
     для запуска из PATH (заменяет ручную ссылку в `~/.local/bin`).
2. **Браузер без загрузки.** Новая переменная `SDO_BROWSER_CHANNEL` передаётся в
   `chromium.launch({ channel })`. Приложение на Windows задаёт `msedge`: Edge есть на любой
   Windows 10/11, поэтому `npx playwright install chromium` не нужен. Без переменной
   поведение прежнее (встроенный Chromium Playwright).
3. **Отладочные скриншоты по флагу.** `debug-profile-*.png` и аналогичные снимки пишутся
   только при `SDO_DEBUG_SCREENSHOTS=1`. Сейчас они пишутся всегда, в рабочую папку, и
   содержат страницу входа: это лишние персональные данные и ошибка записи, если папка
   только для чтения.
4. **Тег `v1.2.0`.** Текущий `v1.1.0` (`f663bab`) старше коммита с `sdo_login` (`0856ba2`),
   поэтому зависимость нужно закрепить на новом теге.

## 5. Запуск сервера в `online-lecture`

### 5.1. Зависимость

В корневом `package.json` (ядро владеет MCP-клиентом) и в `apps/desktop/package.json` (чтобы
`electron-builder` в фазе 4 включил пакет в установщик):

```json
"sdo_mcp": "github:tab11pm/sdo-mcp#v1.2.0"
```

Версия закрепляется тегом; обновление sdo_mcp — осознанная правка этой строки и
`package-lock.json`.

### 5.2. Поиск точки входа

Новая функция в `src/config/mcp-config.ts`:

```ts
resolveBundledServer(deps?): { script: string; packageDir: string } | undefined
```

- через `createRequire(import.meta.url).resolve('sdo_mcp/package.json')` находит каталог пакета;
- точка входа — `<packageDir>/dist/index.js`;
- если путь проходит через `app.asar`, заменяет сегмент на `app.asar.unpacked` (файлы,
  запускаемые отдельным процессом, не могут лежать внутри asar);
- возвращает `undefined`, если пакет не установлен или `dist/index.js` отсутствует.

Зависимости (`resolve`, `exists`) передаются параметрами, чтобы тесты не трогали реальный
`node_modules`.

### 5.3. Порядок выбора команды

`loadMcpConfig()` выбирает первый подходящий источник и запоминает его в новом поле
`McpConfig.source`:

| Источник       | Условие                              | Команда                                       |
| -------------- | ------------------------------------ | --------------------------------------------- |
| `env`          | задан `SDO_MCP_SERVER_PATH`          | разбор строки как сейчас (`splitCommandLine`) |
| `bundled`      | `resolveBundledServer()` нашёл пакет | `process.execPath`, args `[script]`           |
| `user-install` | существует `~/.local/bin/sdo-mcp`    | этот путь                                     |
| `path`         | иначе                                | `sdo-mcp`                                     |

Для `bundled` в окружение сервера добавляется `ELECTRON_RUN_AS_NODE=1`. В Electron
`process.execPath` — бинарник Electron, и переменная превращает его в Node; в CLI это
обычный `node`, для которого переменная ничего не значит. `ELECTRON_RUN_AS_NODE`
добавляется явно, потому что `collectServerEnv` пропускает только разрешённые переменные.

`SDO_MCP_SERVER_CWD` по-прежнему задаёт рабочую папку; для `bundled` по умолчанию она не
задаётся (sdo_mcp получает настройки через окружение, а `dotenv` не перезаписывает уже
заданные переменные).

### 5.4. Канал браузера

Десктопное приложение на Windows передаёт серверу `SDO_BROWSER_CHANNEL=msedge`, если
переменная не задана пользователем. CLI ничего не подставляет.

## 6. Диагностика и сообщения пользователю

### 6.1. Классификация ошибок

`SdoMcpClient` при неудачном подключении бросает `SdoMcpUnavailableError` с полями:

- `reason`: `not_found` (spawn `ENOENT`/`EACCES`, `bundled` не найден), `exited` (процесс
  завершился до ответа, `Connection closed`), `timeout` (рукопожатие MCP не завершилось за
  `connectionTimeout`; сейчас это поле конфигурации читается, но в `ensureConnected` не
  применяется — изменение начинает его применять и закрывает транспорт по таймауту);
- `source` из `McpConfig`;
- `detail`: код выхода и последние ~4 КБ stderr, уже прошедшие `redactSensitiveText`.

Для сбора stderr транспорт создаётся со `stderr: 'pipe'`; поток читается в кольцевой буфер и
не выводится в консоль приложения. Ошибки самих инструментов (`isError` в ответе) остаются
прежними и не считаются недоступностью сервера.

### 6.2. Онбординг

`OnboardingMachine.checkSession`, `submitCredentials` и `openManualSso` различают
`SdoMcpUnavailableError` и прочие ошибки:

- недоступность sdo_mcp → `{ phase: 'failed', message }`, где текст зависит от `reason`:
  - `not_found`: «Компонент входа SDO MCP не найден. Переустановите приложение.»;
  - `exited` / `timeout`: «Компонент входа SDO MCP не запустился. Подробности в журнале: <путь>.»;
- прочие ошибки — как сейчас (форма входа с сообщением).

Экран `failed` уже показывает сообщение и кнопку «Повторить», новых фаз не добавляется.
Путь к журналу передаётся в сообщении как есть (локальный путь пользователя, не секрет).

### 6.3. Файловый журнал ядра

Новый модуль `apps/desktop/src/worker/core-log.ts`:

- пишет в `<AppPaths.logs>/core.log` (каталог уже описан в `AppPaths`, но не используется);
- строки: ISO-время, уровень, сообщение; каждое сообщение проходит `redactSensitiveText`;
- при превышении 1 МБ файл переименовывается в `core.log.1` (одна предыдущая копия);
- ошибки записи журнала не ломают работу ядра.

Что журналируется:

- при старте worker — выбранный `source` и команда сервера (без окружения);
- каждая `SdoMcpUnavailableError` — `reason`, `source`, `detail`;
- непредвиденные ошибки команд онбординга (вместо молчаливого проглатывания в
  `checkSession`).

Пароль, cookies, `sessionToken` и join-URL в журнал не попадают: окружение сервера не
логируется, остальное проходит редакцию.

## 7. Тестирование

Ядро (`tests/config`, `tests/core`):

- `resolveBundledServer`: найден пакет; нет пакета; нет `dist/index.js`; путь через `app.asar`
  переписывается в `app.asar.unpacked`.
- `loadMcpConfig`: приоритет `env` > `bundled` > `user-install` > `path`; для `bundled`
  команда `process.execPath`, args `[script]`, в окружении `ELECTRON_RUN_AS_NODE=1`.
- `SdoMcpClient`: несуществующая команда → `SdoMcpUnavailableError('not_found')`; фикстурный
  сервер, который пишет в stderr и завершается, → `exited` с редактированным хвостом stderr.

Десктоп (`apps/desktop/tests`):

- `OnboardingMachine`: недоступность → `failed` с текстом по `reason`; прочие ошибки —
  прежнее поведение.
- `core-log`: запись, редакция секретов, ротация по размеру, ошибка записи не бросается.
- Ручная проверка: `npm install` на чистой копии ставит `sdo_mcp` с `dist/`; приложение в
  режиме разработки входит без `SDO_MCP_SERVER_PATH`.

sdo_mcp: тесты на выбор канала браузера и на отсутствие скриншотов без флага.

## 8. Требования к упаковке (фаза 4)

Не реализуются здесь, но упаковка обязана их соблюсти:

- `asarUnpack` для `node_modules/sdo_mcp/**` и `node_modules/playwright*/**`;
- Electron fuse `RunAsNode` остаётся включённым (иначе `ELECTRON_RUN_AS_NODE` не работает);
- браузер Playwright в установщик не кладётся — используется Edge через `SDO_BROWSER_CHANNEL`.

## 9. Риски

- **Сборка при `npm install`.** `prepare` требует скачать devDependencies sdo_mcp
  (TypeScript и др.). Для разработки это приемлемо; установщик в фазе 4 собирается заранее,
  у пользователя `npm install` не выполняется.
- **Версия Node в Electron.** sdo_mcp работает на Node из Electron (22+). Если sdo_mcp
  потребует более новый Node, обновляется Electron.
- **Нет Edge.** На Windows LTSC/Server Edge может отсутствовать: тогда sdo_mcp упадёт при
  запуске браузера, это попадёт в журнал как ошибка инструмента. Обход — задать
  `SDO_BROWSER_CHANNEL` пустым и установить Chromium вручную.
