# Автоимпорт расписания ТУСУР — дизайн

**Статус:** на согласовании
**Дата:** 2026-10-02
**Тема:** подключение `timetable.tusur.ru` и упрощение onboarding до «логин + пароль»

## 1. Назначение и критерий успеха

Сделать приложение максимально простым для нетехнического студента: вместо ручного
добавления каждой лекции пользователь один раз вводит логин и пароль, после чего
приложение само находит его группу, забирает онлайн-пары из расписания ТУСУР,
сопоставляет их с курсами SDO и автоматически подключается к нужным лекциям.

Критерий успеха: после первого запуска и одного входа пользователь больше не думает
о лекциях. Список пар можно править, но по умолчанию всё работает само.

## 2. Область и ограничения

Входит:

- вход через SSO `profile.tusur.ru` (общий для SDO и timetable);
- автоопределение группы через авторизованную главную `timetable.tusur.ru`;
- импорт онлайн-пар группы (признак «реализуется в ЭИОС»);
- сопоставление дисциплины с курсом SDO через `course_links`;
- разрешение BBB через существующий SDO MCP `resolve_online_lecture`;
- обновление расписания при запуске и по кнопке;
- ручное добавление пар («разово»/«каждую неделю») и действие «Перенести».

Не входит (без изменений относительно SPEC):

- импорт произвольных календарей и cron-расписаний;
- несколько аккаунтов и пользователей;
- облачный сервис, Telegram, Linux/macOS;
- обход запрета модератора.

## 3. Архитектура и поток данных

```
Onboarding (логин, пароль)
        |
        v
SSO profile.tusur.ru  ──►  общая сессия (.tusur.ru)
        |
        v
TimetableClient: GET / (авторизованная)  ──►  ссылка «Мое расписание»
        |                                         └─► faculty, group
        |
        ├── GET /faculties/<f>/groups/<g>?week_id=<n>  (по неделям)
        │        └─ пары: дата, время, дисциплина, вид, аудитория, ЭИОС, lesson-id
        |
        ├── GET /ocenka/api/v1/lessons/<id>/course_links   ──►  discipline -> sdoCourseId
        |
        v
SDO MCP resolve_online_lecture(courseUrl)  ──►  BBB-активность
        |
        v
TimetableImporter: онлайн-пары + BBB  ──►  Job'ы (source=timetable)
        |
        v
ImportMerger (SQLite): авто-задания + ручные пары + правки (suppressed/edited)
        |
        v
Существующий Scheduler / run-lifecycle
```

Все компоненты импорта живут в `src/timetable/`, не зависят от Electron и тестируются
на фикстурах.

Состав модулей:

- `timetable-client.ts` — сетевые запросы: главная, страница группы по неделям,
  `course_links`.
- `timetable-parser.ts` — HTML -> нормализованные пары; определение недель.
- `online-detector.ts` — признак ЭИОС.
- `course-mapper.ts` — `discipline -> sdoCourseId`; построение Moodle course URL.
- `lecture-resolver.ts` — вызов MCP `resolve_online_lecture`.
- `timetable-importer.ts` — сборка `Job` из онлайн-пар.
- `import-merger.ts` — слияние при обновлении; дедупликация.

## 4. Модель данных

Добавляется третий вид расписания:

```ts
interface ImportedOccurrence {
  date: string;      // YYYY-MM-DD
  joinAt: string;    // HH:MM
  leaveAt: string;   // HH:MM
  room?: string;
  edited?: boolean;     // пользователь правил — refresh не перезатирает
  suppressed?: boolean; // пользователь выключил — refresh не возвращает
}

type Schedule =
  | { type: 'once'; date; joinAt; leaveAt; timezone }
  | { type: 'weekly'; days; joinAt; leaveAt; timezone }
  | { type: 'imported'; timezone: string; occurrences: ImportedOccurrence[] };
```

Расширение `Job`:

- `source: 'manual' | 'timetable'`;
- `origin?: { faculty; group; discipline; sdoCourseId }` — для обновления
  авто-заданий;
- авто-id: `tt:<faculty>:<group>:<sdoCourseId>` (стабилен между обновлениями);
- `target`: `{ type: 'search', courseId: sdoCourseId, courseName: discipline }`,
  после успешного резолва может стать `direct` с точным BBB URL.

Правила:

- `source: 'manual'` refresh не трогает никогда.
- Задания из старой БД без `source` считаются `manual` (безопасная миграция).
- `findActiveOccurrence()` получает ветку `imported`: совпадение по `date` и окно
  `[joinAt, leaveAt)`.
- `occurrenceId` остаётся `jobId:joinAt`, история запусков сохраняется.

## 5. Timetable-клиент, парсинг и сопоставление

Все запросы, кроме главной, публичны; авторизация нужна только чтобы найти ссылку
«Мое расписание».

1. Авторизованный `GET https://timetable.tusur.ru/` -> находим ссылку с текстом
   «Мое расписание» -> извлекаем `faculty` и `group`
   (пример: `http://timetable.tusur.ru/faculties/fvs/groups/574-1` -> `fvs`, `574-1`).
2. `GET /faculties/<f>/groups/<g>` -> из навигации `?week_id=<n>` получаем диапазон
   недель.
3. Для каждой недели — `GET /faculties/<f>/groups/<g>?week_id=<n>`:
   - дата — из заголовка дня (`пн, 28 сент.` с годом из шапки семестра);
   - время — из двух `span` (начало/конец);
   - дисциплина — **полное имя** из `title`/`data-original-title` (`abbr` даёт
     только аббревиатуру вида «ПОПД»);
   - вид занятия — из `class="kind"` («Лекция», «Лабораторная работа», …);
   - аудитория — из `class="auditoriums"`;
   - онлайн-признак — заметка **«реализуется в ЭИОС»**
     (`<span class="note">реализуется в ЭИОС</span>` и tooltip `fa-info-circle`);
   - `data-lesson-id`.
4. Для уникальных онлайн-дисциплин — `GET /ocenka/api/v1/lessons/<id>/course_links`
   -> `sdoCourseId` из `url` (`https://sdo.tusur.ru/auth/edu?id=22413` -> `22413`).
5. `sdoCourseId` -> `https://sdo.tusur.ru/course/view.php?id=<id>` ->
   `resolve_online_lecture(courseUrl)`.

Наблюдение на реальном расписании группы `574-1` (текущая неделя): онлайн-пары —
РМП2 (1 лекция + 2 лабораторные) и РВП (1 лекция); `course_links` даёт
`22413` (РМП2) и `22414` (РВП). Остальные пары — аудиторные, ЭИОС не помечены.

Правило фильтрации: по умолчанию импортируем только онлайн-пары; вид занятия
влияет лишь на отображение. Практики/лабораторные можно добавить вручную.

## 6. Onboarding

```
1. Приветствие
2. Форма: логин/почта + пароль
3. Вход SSO
   ├── сессия валидна -> дальше
   └── капча/2FA -> видимое окно ТУСУР -> после успеха дальше
4. Авто-импорт с прогрессом
   главная -> «Мое расписание» -> недели -> ЭИОС -> course_links -> MCP
5. Результат: список найденных онлайн-пар
   [Подключить]  [Отредактировать]  [Пропустить]
6. Готово: работа в трее + переключатель автозапуска
```

Детали:

- Валидная сессия -> шаг 3 пропускается.
- Логин и пароль хранятся только локально; на Windows — через DPAPI. Сессия — в
  `SDO_AUTH_STATE_PATH`, общий контекст для SDO и timetable.
- Ничего не найдено -> сообщение и предложение «Добавить свою пару» (раздел 7).
- Шаг 5 — единственное обязательное действие; «Отредактировать» ведёт в список.

## 7. Обновление, изменения и добавление

Авто-задания имеют стабильный id-источник, поэтому обновление — это слияние, а не
пересоздание.

Алгоритм merge (при запуске и по кнопке «Обновить»):

1. Тянем онлайн-пары с сайта -> наборы `{date, joinAt, leaveAt}` по дисциплинам.
2. Для каждой дисциплины ищем авто-задание по id-источнику:
   - нет -> создаём, все вхождения с сайта;
   - есть -> сливаем по дате:
     - `edited: true` -> оставляем как есть;
     - `suppressed: true` -> оставляем скрытым;
     - прочие -> заменяем пришедшими;
     - новые даты -> добавляем; пропавшие неотредактированные -> удаляем.
3. `source: manual` не трогаем.
4. Если набор с сайта для дисциплины пуст: авто-задание удаляется, когда нет ни
   `edited`, ни `suppressed` вхождений; иначе остаётся с сохранёнными вхождениями.
5. Показываем сводку: «+2 пары, −1 пара, 1 правка сохранена».

Поведение ручных пар:

- «Разово» (по умолчанию) -> `once` с конкретной датой; отрабатывает один раз и
  уходит в историю, удалять не нужно.
- «Каждую неделю» -> `weekly`; повторяется, пока не выключишь/удалишь.
- «Перенести» на конкретной паре -> одним действием помечает исходное вхождение
  `suppressed: true` и создаёт связанную разовую пару на новое время.
- Удаление авто-пары = `suppressed` (иначе refresh вернёт); удаление ручной —
  реальное удаление.

Дедупликация: если ручная и авто-пара совпадают по (дата, время, дисциплина),
выполняется один вход.

Refresh не трогает активное вхождение; изменения применяются только к будущим.

## 8. Резолв BBB через SDO MCP

- `resolved` -> онлайн-курс подтверждён, задание получает `direct` URL.
- `not_found` -> дисциплина пропускается, уведомление.
- `ambiguous` -> пользователь выбирает точную активность до сохранения.
- `auth_required` -> повторный вход.
- MCP-вызов кратковременный; во время лекции BBB-сеансом управляет ядро (SPEC §3.1).
- browser/context MCP всегда закрываются, фоновых Chromium не остаётся.

## 9. Ошибки и краевые случаи

Принцип: никогда не стирать расписание молча; при ошибке сохраняем последнее
рабочее состояние и даём «Повторить».

Вход/сессия:

- неверный пароль -> сообщение, повтор ввода;
- капча/2FA -> видимое окно;
- истёкшая в фоне сессия -> задание `blocked`, уведомление, задания не теряются.

Timetable:

- сайт недоступен / изменилась разметка -> ошибка парсера, старые пары остаются;
- нет ссылки «Мое расписание» / группа не найдена -> предложение добавить вручную;
- пустой `course_links` у ЭИОС-пары -> «не удалось сопоставить», ручной поиск.

MCP/BBB:

- `ambiguous` / `not_found` / `auth_required` — как в разделе 8;
- преподаватель не открыл комнату -> `waiting_room` до входа или `leaveAt`;
- сетевой разрыв -> не более 3 попыток 5/15/30 секунд;
- удаление модератором -> повторный вход запрещён;
- `leaveAt` — жёсткий предел.

Система:

- повреждение SQLite -> диагностическая копия и восстановление (SPEC §8);
- нет сети к моменту пары -> попытки, затем `failed` и уведомление;
- пробуждение из сна -> вход только если окно `[joinAt, leaveAt)` активно;
- нет прав/места в `%LOCALAPPDATA%` -> понятная ошибка без падения.

## 10. Хранилище и приватность

- Логин и пароль — только локально, пароль шифруется DPAPI на Windows.
- Браузерная сессия, база и логи — только в `%LOCALAPPDATA%`.
- Телеметрии и удалённого сервера нет.
- Автоматизация разрешает только HTTPS и allowlist доменов ТУСУР/SDO/BBB.
- Cookies, query-параметры, join URL и `sessionToken` вырезаются из логов.
- В репозиторий не попадают реальные сессии, персональные данные студентов и
  дампы расписания с личными идентификаторами.

## 11. Тесты

По умолчанию — только локальные фикстуры, никаких живых вызовов ТУСУР. Живой
smoke — вручную и по явному флагу.

Фикстуры (обезличенные): авторизованная главная, страницы группы `574-1` по
неделям, ответы `course_links`, ответы MCP по статусам.

Юниты парсера:

- список факультетов; страница группы; дата + время;
- полное имя дисциплины из `title`, а не `abbr`;
- детект ЭИОС; `discipline -> sdoCourseId`; пустой `course_links`; перечисление недель.

Merge/refresh:

- добавление, перенос, удаление;
- `edited` сохраняется, `suppressed` не возвращается;
- `manual` не трогается; исчезнувшая дисциплина удаляет авто-задание;
- дедуп ручная+авто; миграция старых заданий в `manual`.

Модель/планировщик:

- `findActiveOccurrence` для `imported`;
- разовая ручная пара срабатывает один раз, `weekly` — повторяется;
- «Перенести» = suppress + разовое новое.

MCP (контракт, на фикстурах): `resolved`/`ambiguous`/`not_found`/`auth_required`;
закрытие browser/context.

Интеграция: фикстуры недель -> импортёр -> задания -> `Scheduler.check()` в
подставное время -> `runner.start` только для РМП2/РВП.

Переиспользуем существующие тесты: retry 5/15/30, deadline, occurrence-дедуп,
redaction, backup/recovery.

Имена тестов — по наблюдаемому поведению, например
`marks-eios-lessons-online.test.ts`, `preserves-edited-occurrences-on-refresh.test.ts`.

## 13. Фазы реализации

1. Ядро: клиент, парсер, ЭИОС, маппинг курсов, модель `imported`, импортёр, merge —
   полностью на тестах.
2. MCP-резолв BBB, дедупликация, CLI-команда `import` для ручного smoke.
3. Electron: onboarding, список/правки/«Перенести», DPAPI, автозапуск, трей.
4. Упаковка Windows и E2E.

## 14. Открытые риски

- Точное соответствие «дисциплина -> SDO-курс» и формат course URL проверяются
  контрактным тестом на реальном ответе `course_links`; при расхождении — fallback
  на поиск по названию через MCP.
- Разметка timetable может измениться; парсер должен давать явную ошибку и не
  портить сохранённое расписание.
- Страница группы отдаётся по неделям; горизонт известен только на семестр вперёд,
  поэтому обновление при запуске обязательно.
- Программный вход в SSO может упереться в капчу/2FA; предусмотрено запасное
  видимое окно.
